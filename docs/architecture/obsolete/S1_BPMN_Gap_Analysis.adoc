:author: Architecture Analysis

== Executive Summary

The current S1 BPMN diagram ("Business Process S1 resolve entity mention") models the automated resolution workflow across TED-SWS, ER System, and Entity Resolution Engine (ERE). However, it **omits the link curation phase** documented in the ERS_MDR conceptual flow, resulting in incomplete process semantics.

This document identifies critical gaps and proposes structural improvements to align the BPMN with business reality.

---

== Current State Analysis

=== S1 BPMN Scope

The diagram operates at **L2 (Container/Business Process) level**, showing:

* **Three swimlanes (actors):**
  - TED-SWS Pipeline: Submits entity mention → receives canonical identifier
  - ER System: Validates request, decides if resolution needed, orchestrates ERE call
  - Entity Resolution Engine: Performs resolution matching

* **Happy path flow:**
  [start] → Submit entity → Validate → Check cache? → If No: Send to ERE → Integrate result → Return canonical ID → [end]

* **Decision gate:**
  - "Is resolution required?" (cache hit vs. cache miss)

=== Semantics Assessment

**Strengths:**
* Clear actor separation (pools)
* Message flows labeled (resolution request, resolution result, canonical identifier)
* Simple decision gate for cache logic
* Appropriate granularity for L2 (not too detailed)

**Weaknesses:**
* Tasks are primarily technical, not business-meaningful
  - "Determine canonical identifier" is implementation detail
  - "Integrate resolution result" lacks context
* Single linear happy path; no failure or alternative paths
* No explicit representation of **link curation** or **confidence-based decisions**
* No state management concerns (where does canonical identifier get stored?)

== Gap Analysis: ERS_MDR Reveals Missing Business Logic

=== Source Document: ERS_MDR Conceptual Flow

The ERS_MDR PDF documents a **two-phase resolution workflow** not currently captured in S1 BPMN:

==== Phase 1: Automated Resolution (currently in BPMN)
* TED-SWS submits entity mention for resolution
* ER System receives, validates, registers request
* ERE performs matching and returns **alignment links** with **confidence scores**
* ER System receives resolution result

==== Phase 2: Link Curation (MISSING from BPMN)
* ER System evaluates alignment links returned by ERE
* **Decision gate 1: Prune to acceptance-threshold?**
  - Confidence scores below threshold are filtered or flagged
  - Decision context: "Do we want to prune this response? ERE may provide 100+ links."

* **Decision gate 2: Manual action required?**
  - If all links have confidence ≥ acceptance-threshold: Auto-accept top link
  - Else: **Present to curator for manual decision**

* **Three manual curation actions (MISSING from BPMN):**

  1. **Accept Decision:** Curator selects top confidence link
     - Action: Set confidence to +1 (confirmed)
     - Updates: Canonical Registry (write canonical entity state, endorse the automated integration)
     - Message: "Integrate (write) in the canonical registry the top confidence link, replacing the initially created draft alignment link"

  2. **Reject Decision:** Curator rejects all candidate links
     - Action: Set all link confidences to -1 (rejected)
     - Updates: Link-Store (store rejected links and their -1 confidence)
     - Result: Entity mention remains unresolved; may trigger re-resolution

  3. **Manage Confidence:** Curator adjusts confidence scores for selected links
     - Action: Change confidence values
     - Updates: Both Link-Store (audit trail) and Canonical Registry (applies new confidence)
     - Message: "Update the canonical entity state" with adjusted confidence

* **State Management Consequences (NOT IN BPMN):**
  - Accept path: Canonical Registry receives "integrate top link" command
  - Reject path: Link-Store receives "mark all links as rejected" command
  - Manage path: Both stores updated with new confidence values
  - Feedback loop: Reject + low ERE confidence may trigger re-resolution

=== Critical Semantic Gaps

[cols="1,2,3", options="header"]
|===
| Gap | Current BPMN | ERS_MDR Reality
| **Link Curation Actor** | Not represented | Human/rule-based curator is distinct actor
| **Confidence Scoring** | Implicit (result aggregation) | Explicit (links have confidence values; threshold decisions)
| **Decision Branches** | Single "resolution required?" gate | Multiple gates: threshold acceptance, curation action (accept/reject/manage)
| **State Update Logic** | Implicit "Integrate result" | **Explicit & different**: Link-Store ≠ Canonical Registry
| **Rejection Path** | No failure branch shown | Curator rejects → update link-store with -1 confidence
| **Re-resolution Loop** | Not shown | Reject + low confidence may trigger re-resolution
| **Data Flows** | Generic "result" | Specific: Alignment links (structured), confidence scores, canonical identifier (draft vs. canonical state)
| **Manual Interaction** | Not represented | Curator explicitly selects from candidate links, changes confidence
|===

== Recommendations: How to Improve S1 BPMN

=== Structural Changes Required

==== 1. Add Fourth Swimlane: Link Curation

**Current swimlanes:**
* TED-SWS Pipeline
* ER System
* Entity Resolution Engine

**New swimlane:**
* Link Curation (Human Curator or Rule-Based Engine)
  - Responsible for: Evaluating candidate links, applying confidence thresholds, making accept/reject/manage decisions
  - Rationale: This is an independent actor in the business process; must be explicitly represented in BPMN

**Rationale for separate actor:**
* Link curation is **not internal to ER System** (despite being called by ER System)
* May be performed by humans, specialized rules engine, or hybrid approach
* Has distinct responsibilities and decision authority
* Updates different state stores than automated resolution

==== 2. Add Fifth Swimlane: State Stores (Optional but Recommended)

**New swimlane:**
* State Management (Canonical Registry, Link-Store)
  - Responsible for: Persisting canonical entity state, storing link decisions
  - Rationale: Makes state update consequences explicit and traceable

**Alternative:** Embed state updates as internal ER System tasks (less explicit but simpler)

==== 3. Restructure ER System to Show Two Phases

**Phase 1: Automated Resolution**
* Receive resolution request
* Validate & register
* Check if resolution required (cache logic)
* If yes: Send to ERE, receive alignment links

**Phase 2: Link Curation & State Integration**
* Evaluate links: Prune to acceptance-threshold?
* Pass to curator: Present candidates for manual decision
* Integrate result: Based on curation decision, update appropriate store

==== 4. Add Multiple Decision Gateways

**Gateway 1: "Is resolution required?"**
* Existing in current BPMN
* Yes: → Send to ERE
* No: → Return cached canonical identifier

**Gateway 2: "All links above acceptance-threshold?"**
* New: Evaluate ERE results
* Yes: → Auto-accept top link, integrate to canonical registry
* No: → Present to curator for manual decision

**Gateway 3: "Curation decision?"**
* New: After curator reviews candidates
* Accept: → Integrate to canonical registry
* Reject: → Update link-store (mark -1 confidence), possibly trigger re-resolution
* Manage: → Update confidence in both stores

==== 5. Add Explicit Message Flows with Data Structures

**Current (generic):**
* "resolution request"
* "resolution result"
* "canonical identifier"

**Enhanced (specific):**
* TED-SWS → ER System: "Entity Mention Representation" (structured)
* ER System → ERE: "Resolution Request" (mention + entity type)
* ERE → ER System: "Alignment Links" (list of {mention, cluster, confidence score})
* ER System → Link Curation: "Candidate Links" (filtered/ranked by confidence)
* Curation → Link-Store: "Link Decision" (accept/reject/confidence update)
* Curation → Canonical Registry: "Canonical Entity State" (draft → canonical, integrated links)
* Canonical Registry → ER System: "Canonical Identifier" (final, returned to TED-SWS)

== Proposed S1 BPMN End-State Structure

=== Swimlanes (Actors)

[source]
----
1. TED-SWS Pipeline
   └─ Submit entity mention for resolution
   └─ Receive canonical identifier

2. ER System (Orchestration & Evaluation)
   └─ Receive resolution request
   └─ Validate & register request
   └─ Cache check: Is resolution required?
   └─ (If yes) Send to ERE
   └─ Receive alignment links from ERE
   └─ Evaluate links: Prune to threshold?
   └─ (If threshold met) Integrate to canonical registry
   └─ (Else) Present to curator
   └─ Return canonical identifier to TED-SWS

3. Entity Resolution Engine (ERE)
   └─ Receive resolution request
   └─ Resolve entity (matching, linking)
   └─ Return alignment links with confidence scores

4. Link Curation (Human or Rule-Based)
   └─ Receive candidate alignment links
   └─ Review candidates and their confidence scores
   └─ Make decision: Accept / Reject / Manage Confidence
   └─ Notify ER System of curation decision

5. State Stores (Canonical Registry, Link-Store)
   └─ Receive state update commands
   └─ Persist canonical entity, cluster state
   └─ Persist link decisions and confidence scores
   └─ Provide cached canonical identifiers
----

[cols="1,2,3", options="header"]
|===
| Gate | Condition | Paths
| Cache Hit | "Is resolution required?" | No → Return cached ID; Yes → Send to ERE
| Threshold Acceptance | "All links above acceptance-threshold?" | Yes → Auto-accept; No → Manual review
| Curation Decision | "Curator decision?" | Accept → Canonical registry; Reject → Link-store; Manage → Both
|===

[cols="1,2,3", options="header"]
|===
| From | To | Data / Message
| TED-SWS | ER System | Entity Mention Representation (mention ID, originator, entity type hint)
| ER System | ERE | Resolution Request (structured)
| ERE | ER System | Alignment Links (list of clusters + mentions with confidence scores)
| ER System | Link Curation | Candidate Links (ranked/filtered by confidence)
| Link Curation | Link-Store | Link Decision (accept/reject/confidence update)
| Link Curation | Canonical Registry | Canonical Entity State (draft → canonical, integrated links)
| Canonical Registry | ER System | Canonical Identifier (final draftURI or canonical URI)
| ER System | TED-SWS | Canonical Identifier (return value)

=== Happy Path Sequences

**Path 1: Cache Hit**
----
TED-SWS → ER System: Submit mention
ER System: Check cache → Found
ER System → TED-SWS: Return canonical ID
----

**Path 2: Automated Resolution (High Confidence)**
----
TED-SWS → ER System: Submit mention
ER System: Check cache → Not found
ER System → ERE: Send resolution request
ERE → ER System: Return alignment links (all ≥ acceptance-threshold)
ER System → Canonical Registry: Integrate top link
Canonical Registry → ER System: Return canonical ID
ER System → TED-SWS: Return canonical ID
----

**Path 3: Manual Curation (Below Threshold)**
----
TED-SWS → ER System: Submit mention
ER System: Check cache → Not found
ER System → ERE: Send resolution request
ERE → ER System: Return alignment links (some < acceptance-threshold)
ER System → Link Curation: Present candidates
Link Curation → Link-Store or Canonical Registry: [Accept/Reject/Manage]
  [If Accept] → Canonical Registry: Integrate link
  [If Reject] → Link-Store: Mark -1 confidence, possibly re-trigger
  [If Manage] → Both: Update confidence values
State Store → ER System: Return canonical ID
ER System → TED-SWS: Return canonical ID
----

== BPMN Notation Issues to Address

Per https://en.wikipedia.org/wiki/Business_Process_Model_and_Notation[BPMN 2.0 semantics]:

[cols="1,2", options="header"]
|===
| Issue | Fix
| **Pools vs. Swimlanes** | Current diagram uses subgraph (Mermaid limitation); BPMN-native tools require explicit pools for independent actors (TED-SWS, ER System, ERE, Curation, Stores)
| **Message Flow Direction** | Current uses dotted lines; ensure directionality is clear (who initiates vs. who responds)
| **Task Naming** | Tasks should be business-meaningful. Avoid technical names like "Determine canonical identifier" → use "Select canonical cluster" or "Write canonical entity state"

| **Loop Back** | If re-resolution is triggered, show explicit loop (Reject + low confidence → return to ERE)
|===

== Critical Insights

★ **Insight 1: Two-Phase Architecture**
The ERS_MDR flow reveals that entity resolution is **not a single automated operation**. It's a two-phase workflow: (1) automated matching (ERE), then (2) **human-in-the-loop link curation**. The BPMN must show both phases and their distinct decision paths.

★ **Insight 2: Different State Stores for Different Decisions**
Curation decisions don't all lead to the same place:
- **Accept** → writes to Canonical Registry (confirms automated resolution)
- **Reject** → writes to Link-Store (records decision context, -1 confidence)
- **Manage** → writes to both (updates canonical state + decision audit)

This is a critical architectural distinction currently hidden in "Integrate result."

★ **Insight 3: Curator is Independent Actor**
Link curation is not internal ER System logic; it's a distinct business function. It may be human-driven (regulatory requirement), rule-based (high-confidence automation), or hybrid. **Separating the actor explicitly enables architectural flexibility and clearer responsibility boundaries.**

★ **Insight 4: Confidence Scores Drive Business Logic**
Alignment links have **confidence scores**. These scores are not just metadata; they drive the acceptance-threshold gate and curator decisions. The BPMN must make this explicit (message flows, decision conditions).
