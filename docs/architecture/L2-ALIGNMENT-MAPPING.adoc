= L2 Diagrams: Alignment to Business Glossary

This document maps the newly created L2 sequence and BPMN diagrams to the business glossary, showing how each diagram element corresponds to glossary terms and resolves alignment issues from previous versions.

=== 2. **Responsibility Boundaries (L2 Application Cooperation)**

The L2 diagrams clarify what ERS *owns* vs what ERE *provides*:

**ERS Responsibilities (Authoritative):**
- Accept mention submissions from Originators (entrypoint)
- Orchestrate resolution workflow
- Persist mentions and all alignment decisions (System of Records)
- Manage cluster membership and canonical identifiers (Canonical Entity Registry)
- Expose stable APIs to external systems
- Support curator workflows for manual alignments

**ERE Responsibilities (Pluggable):**
- Execute resolution logic (pairwise matching, clustering, identity assignment)
- Produce AutomaticAlignment results with confidenceScores
- Return only: mentionId + candidateClusters[] + confidenceScores[] + similarityMetrics
- **Do not:** make final identity decisions, expose APIs, persist data, or see curation decisions

=== 3. **Two-Phase Resolution Lifecycle**

The sequence diagram now explicitly shows two phases:

**Phase 1: Automatic Alignment (In-band with mention submission)**
[source]
----
Originator → ERS → SOR (persist mention)
              ↓
          ERE (async): compute alignment + confidence
              ↓
          Decision: confidence >= threshold?
              ├─ YES → AUTO_ACCEPTED (identity assigned immediately)
              └─ NO  → PENDING_CURATION (awaits curator review)
              ↓
          Return canonicalId or temporaryId
----

**Phase 2: Manual Alignment (Out-of-band, curator-driven)**
[source]
----
Curator → Reviews pending alignments (polarity decision)
              ↓
          ERS processes decision
              ↓
          CER updates membership + alignment status
          SOR records curation decision
              ↓
          Mention now has MANUAL_CONFIRMED or MANUAL_REJECTED status
----

=== 4. **Data Persistence Contracts**

The L2 diagrams enforce clear persistence semantics:

**System of Records (Immutable):**
- Stores: Entity Mention Representations (input payloads)
- Stores: AutomaticAlignment Records (mentionId, candidateClusterId, confidence, similarity metrics, evidence)
- Stores: Manual Alignment Records (curator id, polarity decision, timestamp)
- Never deletes; only appends for audit trail
- Serves as system of record for inputs and decisions

**Canonical Entity Registry (Authoritative Identity):**
- Stores: Cluster membership (mention → cluster → canonicalId)
- Stores: Alignment Status (lifecycle state of each alignment)
- Stores: Confidence Scores (for each mention → cluster assignment)
- May be rebuilt from SOR via targeted reclustering or full rebuild
- Is the source of truth for "what identity is this mention assigned to?"

=== 5. **Confidence Threshold as Workflow Decision Point**

The L2 sequence diagram makes explicit a critical business rule from the glossary:

[quote, Business Glossary]
____
*Confidence Threshold:* A configurable minimum confidence score required to accept an automatic alignment. Governs workflow behaviour (auto-accept vs review) and precision/recall trade-offs.
____

The sequence diagram shows:
- ERE produces confidence score for each candidate cluster
- ERS evaluates: `if confidenceScore >= confidenceThreshold`
  - **True:** AUTO_ACCEPTED (assignment persists, canonicalId returned immediately)
  - **False:** PENDING_CURATION (awaits curator review before assignment persists)

This is a critical L2-level contract: ERE provides confidence; ERS applies threshold policy.

=== 6. **Curation as Explicit Alignment Polarity Decision**

From the glossary:

[quote, Business Glossary]
____
*Alignment Polarity:* An explicit indication of equivalence or non-equivalence for an alignment. Used to express whether an asserted correspondence is accepted or rejected. Enables explicit negative decisions, not only positive matches.
____

The L2 sequence diagram shows curation as a two-path decision:
- **ACCEPT** → alignmentPolarity = EQUIVALENT (mention → cluster assignment confirmed)
- **REJECT** → alignmentPolarity = NON_EQUIVALENT (mention is not part of this cluster; may remain unaligned or be re-submitted to ERE)

=== 7. **Removed Ambiguities from Previous Diagrams**

Previous sequence diagram issues:

1. **"Already resolved / cached" branch was confusing:**
   - L2 shows this as: lookup CER for existing mention → cluster → canonicalId assignment
   - If found, assignment already confirmed (either AUTO_ACCEPTED or MANUAL_CONFIRMED in prior execution)
   - If not found, proceed to ERE

2. **ERE internals were unclear:**
   - Previous: "Resolve Entity" (what does this mean?)
   - L2: "Execute Resolution Logic (Pairwise Matching, Clustering, Identity Assignment)" but kept as yellow highlight to show it's a black box from ERS perspective

3. **No curation workflow:**
   - Previous: completely absent
   - L2: explicit out-of-band workflow showing curator reviewing PENDING_CURATION alignments and applying polarity decisions

4. **Persistence ownership unclear:**
   - Previous: mixed component names without clarity on what is authoritative
   - L2: clear annotation that SOR is immutable (append-only for audit), CER is authoritative for identity

Previous BPMN diagram issues:

1. **Used flowchart, not BPMN pools/lanes:**
   - L2: proper swimlanes showing organizational/system boundaries (Originator, ERS, ERE, Curator)

2. **No decision logic:**
   - L2: explicit decision diamonds for threshold evaluation and curation decisions

3. **No curation workflow:**
   - L2: explicit curation pool showing review → decision → result

4. **Mixed levels of abstraction:**
   - Previous: mixed internal components (SOR, REG) with external actors
   - L2: clear separation—external actors (Originator, Curator) in their pools; internal architecture (SOR, CER, Orchestration) grouped within ERS pool

== Glossary Mapping Table (Section I: Information-Oriented)

[cols="1,2,3"]
|===
| Glossary Term | Definition | How L2 Diagrams Implement It

| Real-World Entity | Concrete or abstract object existing independently of the system | Not directly shown; implicit target of all mention references and clustering
| Entity Mention | Record-level information artefact submitted by source system | SEQUENCE: Originator submits; ERS receives and persists in SOR
| Mention Identifier | System-scoped identifier for a mention (as stored artefact) | SEQUENCE: mentionId assigned by ERS when persisting; used throughout to reference the mention
| Entity Mention Representation | Descriptive payload in serialised form (JSON, XML, RDF) | SEQUENCE: submitted by Originator; persisted in SOR; used by ERE for matching
| Entity Representation (abstract) | Descriptive artefact about an entity | Realised as: Mention Representation (from Originator) OR Canonical Entity Representation (derived, optional)
| Cluster | Identity-bearing construct; set of mention assignments to a canonical identifier | SEQUENCE: created/updated by ERE; membership recorded in CER with (mentionId → clusterId → canonicalId)
| Canonical Entity | Logical identity construct scaffolded by a cluster | SEQUENCE: exists only via cluster membership; no separate record; identified by canonicalId
| Canonical Identifier | Stable, universal, system-generated identifier for a cluster and its canonical entity | SEQUENCE/BPMN: assigned by ERS; persisted in CER; returned to Originator as proof of identity
| Canonical Entity Representation | Optional derived/curated descriptive artefact | Not shown in L2 (out of scope for basic resolution workflow); would be derived from SOR mentions
| Alignment | Asserted correspondence between mention and cluster | SEQUENCE: explicitly shown with status lifecycle (AUTO_ACCEPTED, MANUAL_CONFIRMED, MANUAL_REJECTED, PENDING_CURATION)
| Alignment Polarity | Equivalence or non-equivalence indication | SEQUENCE: shown in curation phase (EQUIVALENT = accept, NON_EQUIVALENT = reject)
| Confidence Score | Numeric indicator of system confidence in mention → cluster assignment | SEQUENCE: produced by ERE; evaluated by ORCH against threshold; persisted in SOR
| Confidence Threshold | Configurable minimum score for auto-accept vs curation | SEQUENCE: decision diamond in ORCH evaluating (confidence >= threshold)
| Entity Type | Ontological category classifying entities | SEQUENCE: supplied with mention; passed to ERE for type-aware matching
|===

== L2 Contracts (Derived from Diagrams)

=== Contract 1: ERE Resolution Contract (Input/Output)

**Input:** ResolutionRequest
[source]
----
{
  mentionId: UUID,
  mentionRepresentation: JSON/XML/RDF,
  entityType: string,
  context: {originId, originTimestamp, originator}
}
----

**Output:** AutomaticAlignmentResult
[source]
----
{
  mentionId: UUID,
  candidateClusters: [
    {
      clusterId: UUID,
      confidenceScore: float (0.0-1.0),
      similarityMetrics: {pairwise_scores, evidence_refs},
      evidenceRef: string
    }
  ]
}
----

**Invariant:** ERE does not:
- Persist data
- Assign canonical identifiers
- See curation decisions
- Make final identity decisions (confidence alone is not sufficient)

=== Contract 2: ERS Threshold Evaluation

**Rule:**
[source]
----
if confidenceScore >= CONFIGURED_THRESHOLD:
  alignment_status = AUTO_ACCEPTED
  canonicalId = assign immediately
  response = 200/202 with canonicalId
else:
  alignment_status = PENDING_CURATION
  response = 202 with temporary ID
  signal to curator for review
----

=== Contract 3: CER Membership Assignment

**Invariant:**
[source]
----
For each mention:
  - exactly one current canonical identity (or null if unaligned)
  - alignment_status in {AUTO_ACCEPTED, MANUAL_CONFIRMED, MANUAL_REJECTED, PENDING_CURATION}
  - confidence_score from most recent assignment attempt
  - audit trail of all prior assignments (in SOR)
----

=== Contract 4: Curation Decision

**Rule:**
[source]
----
curator_decision ∈ {ACCEPT, REJECT}
  if ACCEPT:
    alignmentPolarity = EQUIVALENT
    mention → cluster assignment confirmed
    CER updated with MANUAL_CONFIRMED status
  else if REJECT:
    alignmentPolarity = NON_EQUIVALENT
    mention remains unaligned (or re-submitted to ERE)
    CER updated with MANUAL_REJECTED status
----

== Summary

The L2 diagrams resolve all major alignment issues by:

1. **Using consistent glossary terminology** throughout (Alignment, Confidence Score, Manual Alignment, System of Records, etc.)
2. **Showing ERS as the authoritative coordinator**, not just a pass-through
3. **Displaying the full lifecycle:** mention → automatic alignment → threshold evaluation → optional curation → persistent identity
4. **Making implicit policies explicit:** threshold evaluation, polarity decisions, status lifecycle
5. **Separating concerns:** ERE as pluggable black box; ERS as authority; Curator as human loop; SOR as audit trail; CER as source of truth
6. **Using proper BPMN notation** with clear swimlanes and decision logic
7. **Supporting future contracts:** L2 contracts can now be formalized from these diagrams for ER Engine Contract, API contracts, and persistence guarantees
